# Lucy v0.1

Label: wayfinder:map

## Destination

A build-ready v0.1 spec for Lucy, plus a sketched roadmap. v0.1 = local wake word, spoken Sessions with barge-in, clickable Indicator, the news briefing, system questions and app launching, pluggable Providers configured through a TUI, and a Plugin system in which Lucy writes her own Plugins. Success: the news briefing as a hand-written reference Plugin, and "find my Mount Rainier photo" as a Plugin Lucy writes herself.

Spec: [spec.md](spec.md) (ready-for-agent, 2026-11-13), synthesised from tickets 01–22; open tickets 23–27 may still adjust defaults.

## Notes

- Rust, open source from day one, MIT/Apache-2.0; copyleft only out of process (ADR 0003), Linux + Hyprland/Wayland first; nothing personal hard-coded.
- Subscription-backed by default, no pay-per-use APIs (see `docs/adr/0001-subscription-backed-providers.md`). STT, Thinking and TTS are configurable Providers; each Thinking kind runs one native process per Session (no transport axis).
- Default thinking Provider: Claude Code, persistent per Session; Codex selectable. Herdr is out of scope for v0.1.
- Lucy is autonomous, not a coding assistant: when she meets something unknown she researches, builds and tests on her own and comes back with what she *can* do. She asks the user only for what only they can give (which platform, sign-in, approval), never to guide how to connect.
- Not AI everywhere: the fast tier understands the request and picks a Plugin by reading Manifests in one call; Plugins themselves are mostly plain code. When no Plugin fits, Lucy asks clarifying questions, then the advanced tier researches and writes one. Every new or changed Plugin needs the user's yes/no approval before use, with no exceptions (read-only included). Lucy only uses permitted access (official APIs, the user's own sign-in, the site's terms); she never works around restrictions. When research finds a platform can't be accessed (API limits or terms), Lucy says so plainly and offers the best permitted fallback, such as opening the site in the browser for the user to search.
- Two Model tiers (fast, advanced). Setup detects installed tools (claude, codex…) and recommends models per tier; the user chooses.
- Plugins run as separate processes, Rust by default, speaking MCP over stdio; Claude and Codex Delegates use their native clients (stream-json, app-server); Zed's Agent Client Protocol only for agents that speak it natively ("ACP" also names IBM's archived protocol; say "Zed-ACP").
- Actions go through Lucy's own MCP tool server, which proxies approved Plugin tools beside a few Built-in tools (ADR 0005); no raw shell in v0.1. Risky actions (send, delete, spend) need a spoken Confirmation, heard by Lucy's runtime, never relayed by the model.
- STT default local Whisper (Superwhisper optional); TTS default Piper; wake word always local.
- Memory is plain markdown under `~/.local/share/lucy/memory/`. Exploration is a normal Session with an offer to save notes to a configured folder.
- Session ends on Indicator click, a closing phrase, or ~20s silence (configurable).
- Hyprland 0.56 config is Lua (`hl.layer_rule()`); anything Lucy ships or documents for Hyprland targets that syntax.
- Lucy never calls itself "Claude Code …" or implies vendor endorsement. Re-check Anthropic and OpenAI terms, and the news Source catalogue's terms flags, before any release (both vendors changed theirs in Nov 2026).
- Vocabulary: `GLOSSARY.md`. Grilling sessions use the `grilling` and `domain-modeling` skills.
- Not a git repo: research findings live in `research/<name>.md` beside this map rather than on branches.

## Decisions so far

- [What exactly is the news briefing: sources, length, tone, greeting?](issues/11-news-briefing.md): on request; official feeds only (front-page scraping breaks most sites' terms), with a vetted Source catalogue flagged for AI-summary permission, defaulting to CNN, NPR and Sky; the fast tier speaks the top 1–2 stories in one or two sentences and opens the Sources' front pages; Sources that can't be read get an honest "their rules" plus an offer to open the page; Plugin-owned preferences via `set_preference`; detailed roundup from feed descriptions only; an editable `persona.md` (default jovial with a little sass) whose name comes from Lucy's first-run self-introduction.
- [How does Lucy write a new Plugin when nothing can handle a request?](issues/20-plugin-authoring-loop.md): Rainier is split into an honest-limit check (Google Photos → "I can't search it", open its search page) and an authoring check (local Plugin over a partial Takeout); the Session stays open (Listening, silence timer paused, amends 10) with progress as notifications only (config toggle), never spoken; the Delegate is Landlock-sandboxed with open network and no user data before Approval, using `report_progress`/`ask_user`/`submit_plugin`/`cannot`; Approval in the same Session, then the original request is answered and validated ("Is that the one?"); 20 min budget, one build at a time, builds survive Session end; credentials in Secret Service as env vars, no OAuth in v0.1; template folder + authoring brief, no SDK crate.
- [How is the code split into Rust crates, and how do lucyd and lucy talk to each other?](issues/12-crate-architecture.md): `lucyd` owns audio, Session, MCP server, state and children; `lucy` (CLI/TUI) and a separate `lucy-indicator` are clients of one public NDJSON JSON-RPC socket (versioned, schema in the published `lucy-ipc`, no transcripts; ADR 0006); the model reaches MCP through a stdio `lucy mcp-relay` to a private socket; setup tests run in lucyd; 5 crates (3 binaries + `lucy-ipc`, `lucy-config`); systemd user units on `graphical-session.target`, with notifications whenever no Indicator is connected; `lucy listen` added; cpal stream naming fixed upstream.
- [How does a Session move between listening, thinking and speaking, including interruptions?](issues/10-session-lifecycle.md): Idle/Listening/Thinking/Speaking/Confirming, with Thinking vs Speaking set by whether audio plays; Barge-in by sustained speech or instantly by the Wake word (`barge_in` config); next message notes what the user heard; confirmed tools run to completion; 20 s silence timer only in Listening, 8 s after the Wake word; closing phrase only via `end_session`; Indicator per state; spoken error handling.
- [What is the default wake phrase, and how does a user get a different one?](issues/16-wake-phrase.md): "Hey Lucy" by default; any LiveKit v2 `.onnx` via config plus a "train your own" doc, and one extra published "Lucy" model; the engine is not a Provider; the maintainer trains on a rented GPU and commits the models plus training config under `models/wake/`.
- [Which tools does Lucy provide in v0.1, and which need a spoken "yes"?](issues/09-tool-catalogue.md): Plugin tools proxied as `<plugin>__<tool>` on Lucy's MCP server; Confirmation and Approval heard by Lucy's runtime, never the model (local yes-match, 8 s silence = no; ADR 0005); optional `confirm_prompt` in the Manifest (amends 19); Built-in tools `open_url`, `launch_app`, `system_status`, `request_plugin`, `manage_plugin` (remove confirms), `end_session`; no `speak`/`read_page`; `confirm` not overridable.
- [How are Providers and configuration structured, and what does the v0.1 TUI cover?](issues/08-provider-config.md): three Provider kinds (STT, Thinking per Model tier, TTS), no transport axis; one TOML at `$XDG_CONFIG_HOME/lucy/config.toml`, no stored secrets; API-billing env scrubbed and the subscription re-verified on each new `claude` version (never `--bare`); `ort` on tract by default; PipeWire required for barge-in by default; Superwhisper optional; TUI = setup, Provider status, Approval revoke. Claude/Codex Delegates use native clients, not Zed-ACP (ADR 0002 amended).
- [Does the full voice loop (wake word → speech-to-text → Claude → speech) feel fast enough?](issues/07-voice-loop-prototype.md): yes. The user judged it natural; budget is speech end → first audio ≤ 2.5 s (700 ms endpoint, ≤150 ms STT, ≤1.5 s Claude first token, ≤100 ms Piper per sentence); sentence chunking only, no fillers. Barge-in uses the stream-json control interrupt (6 ms, process and context survive), with SIGINT plus respawn as fallback. The Piper server must bind 127.0.0.1. AUR `piper-tts` is currently uninstallable (noted on 17). Measurements split into 23–26.
- [What does a Plugin's Manifest contain, and how are Plugins chosen, approved, updated and removed?](issues/19-plugin-manifest-lifecycle.md): own `manifest.toml` checked against MCP `tools/list`; one fast-tier call picks plugin+tool+args (or answers, clarifies, or hands to authoring); Approvals hash-pinned outside the Plugin, required for shipped Plugins too (ADR 0004); Landlock filesystem enforcement; `confirm` per tool; Lucy edits only her own Plugins; Plugins live for one Session.
- [Which licence does Lucy ship under, given Piper and espeak-ng are GPL-3.0?](issues/17-licence.md): MIT/Apache-2.0, with copyleft only out of process, enforced by cargo-deny (ADR 0003). Lucy supervises the user-installed upstream `piper-tts` HTTP server and offers to install it with approval, choosing the method from the distro detected at runtime via `/etc/os-release` (AUR `piper-tts` on Arch, otherwise `uv`/`pipx`), falling back to text only. Default and recommended voices are permissive only (`cori-medium`).
- [Should Plugins and agent delegation use MCP, A2A, or something else?](issues/21-agent-protocol.md): Lucy owns her Plugin and delegation interfaces (Manifest is the source of truth) with protocols as adapters: Plugins over MCP stdio (`rmcp`), delegating to local agents over Zed's Agent Client Protocol (`claude-agent-acp`, `codex-acp`); A2A deferred to remote agents; Herdr stays bespoke. Amended by 08: Claude/Codex Delegates use native clients, not Zed-ACP.
- [Can a personal app search a user's whole Google Photos library today?](issues/22-google-photos-access.md): no. Since Mar 2025 the Library API reads only app-created media, the Picker API makes the user search, and scripting photos.google.com breaches Google's terms. Recommended: the photo Plugin searches local photo folders (library or Takeout) by GPS/date/filename, falling back to opening Google Photos search in the browser.
- [How should Lucy respond to Anthropic's ambiguous terms on driving a user's own Claude subscription?](issues/18-claude-terms-response.md): Claude subscription stays default (users run Lucy on their own machines with their own accounts); single-user; acts only when spoken to; API-key Providers not a v0.1 priority.
- [Do Anthropic's and OpenAI's terms allow an open-source tool to drive a user's own logged-in Claude Code and Codex CLIs?](issues/15-subscription-terms.md): OpenAI explicitly allows it via Codex app-server (one user, local, free); Anthropic's text is ambiguous for Lucy driving the user's own `claude -p`, so ADR 0001's Claude half is at moderate risk pending a decision. Neither allows credential handling, proxying or multi-user use.
- [Which voice-activity detector should Lucy use, and how strict is the barge-in gate?](issues/14-vad-barge-in.md): Silero VAD v6.2 behind a `Vad` trait (earshot A/B in 07); barge-in at p≥0.7 for 300 ms (≥0.85 for 500 ms while AEC unconverged), duck TTS on first frame; end of utterance after 700 ms silence. Thresholds are starting points to tune.
- [How should Lucy own microphone capture and speaker playback from Rust?](issues/13-audio-io.md): `cpal` 0.18 (PipeWire → PulseAudio → ALSA), both streams in one PipeWire group for drift correction; 16 kHz mono f32 internally, TTS resampled with `rubato` for the AEC reference; behind an `AudioIo` seam.
- [Can local Whisper, Piper and the Superwhisper adapter respond fast enough on this machine?](issues/05-local-stt-tts.md): yes. whisper-rs (Vulkan) per utterance after VAD, `small.en` on GPU / `base.en` on CPU (~0.1 s); Piper `en_GB-cori-medium` (<100 ms first audio) as a persistent out-of-process helper because Piper/espeak-ng are GPL-3.0; Superwhisper via `transcribe FILE` only.
- [Which local wake-word engine works from Rust for a custom word like "Lucy"?](issues/01-wake-word-engine.md): LiveKit WakeWord v2 via `livekit-wakeword` (Apache-2.0 code and weights) with a project-trained `lucy.onnx`, pinned to a git rev until v2 reaches crates.io; sherpa-onnx keyword spotting is the runner-up.
- [How does a long-running Claude Code instance behave (speed, Lucy's tools, permissions, plan limits), and how does Codex compare?](issues/03-claude-code-persistent.md): one stream-json `claude -p` per Session, pre-spawned on the Wake word, isolated config with only Lucy's MCP server, `ANTHROPIC_API_KEY` stripped; warm first token ~0.6–1.5 s. Codex via `codex app-server` over stdio.
- [How do we get echo cancellation for voice interruption with PipeWire, from Rust?](issues/02-echo-cancellation.md): in-process WebRTC AEC3 (`webrtc-audio-processing` 2.x) with Lucy playing her own TTS as the reference; PipeWire's module is opt-in only; VAD is separate; only Lucy's own voice is cancelled in v0.1.
- [Which Rust toolkit can draw a clickable bottom-right Indicator on Hyprland?](issues/06-indicator-toolkit.md): smithay-client-toolkit layer-shell + tiny-skia overlay, Omarchy theme colours, notification fallback on GNOME; gtk4-layer-shell runner-up.
- [How does Herdr accept agent requests and return replies?](issues/04-herdr-interface.md): optional attach-to-existing-agent transport over Herdr's socket API; no streaming and the reply is scraped from the screen, so persistent Claude Code stays the default.

## Not yet specified

- **Learning from repetition**: noticing Lucy keeps doing the same multi-step work and proposing a Plugin for it unprompted (as opposed to on request).
- **Email & calendar access**: Claude connectors vs IMAP/CalDAV vs Google APIs; likely Plugins rather than Built-in tools (09); the Provider model is settled (08). Includes the Google OAuth model (each user's own Cloud project vs a shared verified client; 7-day token expiry in Testing). v0.1 has no general OAuth flow; credentials are Secret Service env vars (20).
- **Content search in photos**: matching "photos of mountains" without GPS needs a local vision/CLIP model, a new local Provider.
- **Memory**: schema, what gets remembered, how facts are learned and corrected. Meanwhile the user's Persona lives in `persona.md` and news preferences live in the news Plugin's state (11); Memory may take these over.
- **Publishing**: AUR/packaging and install story for Lucy herself; licence and the Piper install approach are settled in 17. Includes whether wake models move from the repo to release assets or CI training (16).
- **Parakeet STT**: whisper.cpp now ships Parakeet TDT 0.6B v3; evaluate once whisper-rs exposes it.
- **Further Providers**: optional cloud voices, non-Hyprland desktops (is a notification fallback enough on GNOME?), an optional Omarchy shell plugin for a richer Indicator/bar widget.

- **Cancelling other system audio**: using speaker output as an extra echo reference so music/video don't trigger the wake word or barge-in.

- **Resuming after a false interruption**: continue Lucy's reply from where TTS stopped, rather than just returning to listening.

- **Proactive behaviour**: opt-in turns Lucy starts herself (e.g. a morning briefing unprompted), for a later release.

- **Host-level network enforcement for Plugins**: v0.1 only declares and shows network hosts (Landlock restricts by port, not host); enforce per host later (e.g. a proxy or network namespace).

- **Plugins running between Sessions**: background or long-lived Plugin work outside a Session; v0.1 stops Plugins at Session end. Pairs with proactive behaviour.

## Out of scope

- **Herdr transport**: attaching to agents in Herdr panes; replies are screen-scraped with no streaming and Lucy can't inject her MCP server, so it is a poor fit for spoken turns (decided in [How are Providers and configuration structured, and what does the v0.1 TUI cover?](issues/08-provider-config.md)). Roadmap item.
- **Raw shell**: an opt-in shell for the thinking model. Plugins cover real needs and shell is the riskiest surface (decided in [Which tools does Lucy provide in v0.1, and which need a spoken "yes"?](issues/09-tool-catalogue.md)). Roadmap item.
- **Type-any-word wake engine**: an optional sherpa-onnx open-vocabulary engine so users can change the Wake word without training. Weak recall on short words and a second engine to maintain (decided in [What is the default wake phrase, and how does a user get a different one?](issues/16-wake-phrase.md)). Roadmap item.
