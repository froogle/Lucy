# Can an open-source tool drive a user's own logged-in Claude Code and Codex?

Ticket: `issues/15-subscription-terms.md`. All sources below are primary (Anthropic and OpenAI pages) and were read on **2026-11-12**. **This is not legal advice.** The aim is to show what the text says and where it is unclear.

## Bottom line

- **OpenAI / Codex: the path is documented and sanctioned, with conditions.** OpenAI publishes "ChatGPT plan usage in your open-source app", which includes a page on wiring Codex app-server to a user's ChatGPT-plan token, plus binding **Sign in with ChatGPT Terms** (effective 2026-11-04). Separately, the Codex app-server docs present it as the way to build "a deep integration inside your own product", and its own `account/login/start` offers ChatGPT login. Lucy fits if it stays local, single-user, free, and does not hand the plan out as a general API.
- **Anthropic / Claude Code: unresolved, and the text leans against.** Anthropic explicitly allows a user to sign in to the *unmodified* `claude` binary with their own subscription, and documents scripted `-p` use and `setup-token` "for CI pipelines and scripts". But the same page says third-party developers' products "should use API key authentication" and that Anthropic "does not permit third-party developers to … route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users". The Agent SDK page says third parties may not "offer claude.ai login or rate limits for their products" unless approved. Whether a local, open-source tool that spawns the user's own `claude` falls inside those sentences is **not answered by the text**. Only Anthropic can settle it.

## (a) A user personally scripting their own CLI

### Anthropic

- The Consumer Terms forbid automation unless Anthropic permits it. §3 says you may not access the Services:
  > "Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it, to access the Services through automated or non-human means, whether through a bot, script, or otherwise."
  — [Consumer Terms](https://www.anthropic.com/legal/consumer-terms), effective Oct 8, 2025. **Note:** the copy served to this machine was the UK variant ("These Terms apply to you if you are a consumer who is resident in the United Kingdom"). The version for other regions was not checked.
- The Claude Code docs arguably supply that explicit permission for Claude Code itself:
  > "`CLAUDE_CODE_OAUTH_TOKEN` … A long-lived OAuth token generated by `claude setup-token`. Use this for CI pipelines and scripts where browser login isn't available."
  > "This token authenticates with your Claude subscription and requires a Pro, Max, Ultra, Team, or Enterprise plan."
  — [Authentication](https://code.claude.com/docs/en/authentication)
- The legal page scopes OAuth to "ordinary use":
  > "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Ultra, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications."
  > "Advertised usage limits for Pro, Max, and Ultra plans assume ordinary, individual usage of Claude Code and the Agent SDK."
  — [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- **Reading:** a person running `claude -p` from their own scripts appears permitted, because Anthropic documents it. "Ordinary, individual usage" is undefined. An always-listening assistant that fires on every utterance might or might not count as ordinary. That bears on rate limits more than on permission.

### OpenAI

- The Terms of Use (effective Jan 1, 2026, non-EEA/UK version) say you may not:
  > "Automatically or programmatically extract data or Output (defined below)."
  > "Interfere with or disrupt our Services, including circumvent any rate limits or restrictions or bypass any protective measures or safety mitigations we put on our Services."
  — [Terms of Use](https://openai.com/policies/row-terms-of-use/)
- The Codex docs treat programmatic use as normal, but steer automation toward API keys:
  > "Use API key authentication for programmatic Codex CLI workflows, such as CI/CD jobs. Don't expose Codex execution in untrusted or public environments."
  — [Codex auth](https://learn.chatgpt.com/docs/auth)
- **Reading:** Codex `exec` and app-server are built to be driven by programs, so personal scripting looks fine in practice. The "programmatically extract … Output" clause, read literally, reaches any scripted use. It is general Terms-of-Use wording that the product docs contradict in spirit. That is an ambiguity, not a prohibition we can rely on either way.

## (b) A published open-source project whose users bring their own login

### Anthropic: the key clauses

From [Legal and compliance → Authentication and credential use](https://code.claude.com/docs/en/legal-and-compliance):

> "**Developers** building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication through Claude Console or a supported cloud provider. Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow."

> "… Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code as described under *Can customers offer Claude Code in their products?* above."

> "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice."

The same page, under "Can customers offer Claude Code in their products?":

> "Unless we've mutually agreed otherwise, preinstalling or running Claude Code in your products or services (e.g. in hosted sandboxes or other agent infrastructure) requires agreeing to our Commercial Terms of Service and complying with the conditions below:"
> "**The Claude Code binary must not be modified.** … customers may not remove, disable, or restrict any authentication method built into it …"
> "**Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf.** Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential …"

From [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview):

> "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods described in the Quickstart instead."

From the [Usage Policy](https://www.anthropic.com/legal/aup) (effective Nov 12, 2026, which is today, so it was just revised), under "Do Not Abuse Our Platform":

> "Resell, proxy, or otherwise provide access to Claude through unauthorized means, including services that route requests through consumer subscriptions or misrepresent the product or client being used"

### What counts in Lucy's favour

- Lucy never handles the claude.ai login. The user signs in with `claude` itself, which meets "sign-in to a Claude account must complete through Anthropic's own flow".
- Lucy runs the **unmodified** binary the user installed, and the page says the policy does not "prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription". It even allows that "where a platform hosts Claude Code".
- Every user uses their own subscription. Nobody pays for, resells or pools usage.
- Lucy is not a "service" in the AUP sense: there is no server and nothing is proxied.

### What counts against

- Lucy is a "product … that interact[s] with Claude's capabilities", and the stated expectation for such products is "should use API key authentication".
- A literal reading of "route requests through … plan credentials on behalf of their users" covers what Lucy does: Lucy's code decides when to send a request, and it rides the user's Max plan.
- The Agent SDK note's ban on offering "claude.ai login **or rate limits**" in third-party products is broad. Lucy's selling point (ADR 0001) is exactly that its thinking runs on the user's subscription limits. Lucy uses the CLI rather than the SDK, but the SDK docs themselves call the CLI subprocess the same agent loop for other languages.
- The "Can customers offer Claude Code" carve-out is written for businesses that preinstall or host Claude Code under the **Commercial** Terms. It is unclear whether an MIT/Apache project that tells users "install `claude` and log in" is "running Claude Code in your products". If it is, the conditions (unmodified binary, each user's own credentials) look satisfiable. But the gate is "requires agreeing to our Commercial Terms", and how an unincorporated open-source project would do that is unclear.

**Ambiguity, stated plainly:** the text both protects "an end user signing in to the unmodified binary with their own subscription" and forbids "third-party developers … rout[ing] requests through … plan credentials on behalf of their users". Lucy sits exactly between the two, and nothing in the primary sources resolves which sentence governs a local, open-source orchestrator. The page invites the question: "For questions about permitted authentication methods for your use case, please contact sales."

### OpenAI: an explicit open-source path

OpenAI documents plan usage for open-source tools directly.

- [SIWC quickstart](https://developers.openai.com/siwc/quickstart):
  > "**For open-source developers:** Let users run AI workloads in your tools with their ChatGPT plan, without requiring them to provide an API key."
  > "Sign in with ChatGPT is currently available to selected commercial partners through a limited trial. ChatGPT plan usage is available to all open-source partners and selected private clients."
- [ChatGPT plan usage overview](https://developers.openai.com/siwc/token-sharing-open-source):
  > "These docs explain ChatGPT plan usage for open-source and locally hosted apps. If you're interested in offering it in a paid or remotely hosted app, complete the interest form."
- [Codex app-server (SIWC)](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) shows how to start `codex app-server` with a `model_provider` whose `env_key="ACCESS_TOKEN"` holds the user's SIWC token, and says the `clientInfo.name` "should match the `agent_name_hint` that your app sends as part of new user registration flow."
- The [Sign in with ChatGPT Terms](https://openai.com/policies/sign-in-with-chatgpt-terms/) (effective Nov 4, 2026) bind any app using that scope. §3.1, "ChatGPT plan usage":
  > "You must not enable or encourage: Creating multiple accounts, splitting usage, rotating accounts, or otherwise bypassing usage limits. Pooling, transferring, reselling, gifting, or sharing ChatGPT plan usage or Authentication Tokens … Using one user's subscription to fulfill another user's requests."
  > "**User control.** Requests must originate from the user's local runtime or a remote runtime only that user controls."
  > "**User authorization.** Requests must be for the authenticated user and arise from their activity or expressly authorized automations or background processes. Obtain express consent before background use. Another user's activity must not trigger requests to the authenticated user's account."
  > "**Connected application only.** Use the user's plan only for the application they connected. Do not provide general-purpose API access for other tools or unrelated requests."
  > "**No charge.** Users must be able to use their ChatGPT plan through SIWC without paying you or upgrading to a paid version of your application."

  §1: "Use your app's own name during sign-in and activation. Do not impersonate OpenAI, another application or entity, or another open-source project." and "Any persistent storage of Authentication Tokens must be local and under the user's control, not in a remote or managed environment."
- **Plan eligibility.** The quickstart names "Eligible ChatGPT Plus and Pro users". The Plus five-hour limit is shared across every app: "Usage in one app contributes to the same five-hour usage total, and no app receives a separate allowance" ([Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)).

**The other OpenAI route: Codex's own login.** The [app-server docs](https://learn.chatgpt.com/docs/app-server) say:
> "Use it when you want a deep integration inside your own product: authentication, conversation history, approvals, and streamed agent events."

They list the `chatgpt` auth mode: "Codex owns the ChatGPT OAuth flow, persists tokens, and refreshes them automatically". They also add:
> "If you are developing a new Codex integration intended for enterprise use, please contact OpenAI to get it added to a known clients list."

So driving the user's existing `codex login`, as planned in `research/claude-code-persistent.md`, is the documented integration surface. **Unclear:** whether an app using Codex-managed `chatgpt` login (rather than its own SIWC registration) is bound by the SIWC Terms. Their wording ("your use of Sign in with ChatGPT … in an application you develop") suggests not, but following them anyway costs Lucy little.

**OpenAI ambiguities:**
1. The "Request a client ID" page says SIWC "is currently offered to a select group of commercial partners". The open-source flow, by contrast, uses self-service dynamic registration (`client_id=dynamic_agent_client`), and the quickstart says plan usage is "available to all open-source partners". Whether "open-source partners" means any open-source project or a vetted list is not stated.
2. The SIWC Terms §3.1 "No charge" rule is easy for an MIT/Apache project. It would matter if Lucy ever had a paid tier.

## (c) What Lucy must avoid, from both vendors

| Avoid | Source |
|---|---|
| Touching the user's login: never collect, store, copy, or forward `~/.claude/.credentials.json`, a `setup-token` token, or `~/.codex/auth.json` | Anthropic: "developers may not collect, store, or intermediate Claude.ai credentials or session tokens". Codex: "treat `~/.codex/auth.json` like a password … Don't commit it, paste it into tickets, or share it in chat." |
| Bundling or shipping any credentials, or one maintainer key for all users | Anthropic: "Each end user must authenticate with their own …". OpenAI Terms of Use: "You may not share your account credentials or make your account available to anyone else" |
| Building Lucy's own claude.ai OAuth or login screen | Anthropic: "does not permit third-party developers to offer Claude.ai login into their own applications" |
| Modifying, patching, or wrapping the `claude` binary to disable auth methods | Anthropic: "The Claude Code binary must not be modified." |
| Proxying: exposing Lucy's provider as an HTTP/OpenAI-compatible endpoint for other tools, or running it as a hosted or remote service | Anthropic AUP: "Resell, proxy … including services that route requests through consumer subscriptions". SIWC §3.1: "Do not provide general-purpose API access for other tools or unrelated requests." |
| Multi-user use: one subscription serving several people, such as a household, guests, or a shared machine | Anthropic Consumer Terms: "may not … make your Account available to anyone else". SIWC §3.1: "Using one user's subscription to fulfill another user's requests" and "Another user's activity must not trigger requests to the authenticated user's account." |
| Usage-limit evasion: rotating accounts or splitting load to stretch limits | OpenAI Terms of Use: "circumvent any rate limits". SIWC §3.1. Anthropic AUP: "Intentionally bypass or interfere with capabilities, restrictions …" |
| Misrepresenting the client, e.g. spoofing Claude Code's or Codex's client identity, or calling claude.ai or ChatGPT endpoints directly with the user's OAuth token | Anthropic AUP: "misrepresent the product or client being used". SIWC §1: "Do not impersonate OpenAI, another application …" |
| Branding Lucy as "Claude Code …" or using Anthropic or OpenAI logos | Anthropic legal page, "Using the Claude Code name and logo". Agent SDK branding guidelines: "Not permitted: 'Claude Code' or 'Claude Code Agent'". SIWC §5 |
| Charging for the subscription-backed path | SIWC §3.1 "No charge". Anthropic: "may not pay for, resell, or intermediate Claude usage" |
| Background or unprompted requests without consent | SIWC §3.1: "Obtain express consent before background use." |

## What the user might do

1. **Ask Anthropic.** The legal page gives a channel ("contact sales"). Describe Lucy precisely: a local, open-source Linux app that spawns the user's own unmodified `claude -p`, with the user logging in via `claude` itself, single-user, no proxying, no charge. Ask whether this is "ordinary use" or needs approval under the Agent SDK note. Get the answer in writing.
2. **Hedge in the product while waiting.** Keep API-key Providers as first-class, as ADR 0001 already allows. Consider making Anthropic's subscription path opt-in, with a plain-language note that the user is responsible for their own Anthropic terms. Make no claim that Anthropic sanctions it.
3. **Prefer the OpenAI path that is explicitly sanctioned.** Either keep using the user's `codex login` through app-server (the documented integration) with a stable `clientInfo.name = "lucy"`, or register via SIWC open-source dynamic registration. Either way, follow the SIWC §3.1 rules.
4. **Design for one speaker per subscription** (see the new questions below).
5. **Re-check before release.** The Anthropic Usage Policy changed today (2026-11-12), and the SIWC Terms took effect on 2026-11-04. Both vendors note that terms change and enforcement can come "without prior notice".
